# Bailanysta

Полноценная соцсеть: посты, лента, лайки, комментарии, подписки, уведомления, загрузка фото, генерация контента через AI и собственная система аккаунтов.

## Описание проекта

Тестовое задание — соцсеть, выполненная поэтапно: от простой формы создания постов до полнофункционального приложения с базой данных, авторизацией и множеством дополнительных возможностей. Проект сделан на Next.js — фронтенд и бэкенд в одном приложении.

## Функциональность

**Базовый уровень:**
- Регистрация и вход по логину и паролю
- Создание, редактирование и удаление постов
- Лента постов с поиском по тексту
- Роутинг между страницами (лента / профиль)
- Собственный бэкенд (API-роуты Next.js), обращение к внешним сервисам только с сервера

**Расширенные возможности:**
- Лайки (один пользователь — один лайк на пост, можно снять)
- Комментарии к постам (добавление и удаление своих)
- Подписки на других пользователей
- Уведомления о лайках, комментариях и новых подписчиках
- Загрузка фото к постам
- Смена логина, пароля и аватарки в настройках профиля
- Генерация текста поста через AI (Google Gemini) по теме
- Тёмная/светлая тема
- Скелетоны при загрузке ленты

## Стек технологий

- **Next.js** (App Router) — фронтенд и бэкенд в одном проекте
- **React** — интерактивность интерфейса
- **Tailwind CSS** — стилизация, включая тёмную тему и адаптивный дизайн
- **Postgres (Neon, через Vercel Storage)** — хранение пользователей, постов, комментариев, лайков, подписок и уведомлений
- **Vercel Blob** — хранение загруженных фото (постов и аватарок)
- **bcryptjs** — хеширование паролей
- **Google Gemini API** — генерация текста постов
- **TypeScript** — не использовался, проект написан на обычном JavaScript/JSX ради простоты (первый опыт в разработке)

## Почему выбран этот стек

- **Next.js** выбран, чтобы не разворачивать отдельный бэкенд-сервер: фронтенд и API-роуты живут в одном проекте, что упрощает разработку и деплой для одного разработчика без опыта.
- **Postgres (через Vercel Storage / Neon)** выбран после того, как выяснилось, что хранение данных «в памяти» ненадёжно на serverless-платформе Vercel — данные сбрасывались между вызовами функций. Postgres даёт постоянное надёжное хранилище с минимальной настройкой прямо из панели Vercel.
- **Vercel Blob** выбран для хранения фото, так как он нативно интегрирован с Vercel и не требует настройки отдельного облачного хранилища (S3 и т.п.).
- **Google Gemini** выбран вместо изначально запланированного OpenAI, так как на аккаунте OpenAI закончился баланс — у Gemini есть бесплатный лимит запросов, достаточный для тестового задания.
- **Tailwind CSS** ускоряет стилизацию без написания отдельных CSS-файлов, что было важно при ограниченном сроке.
- **Без TypeScript** — сознательный выбор для снижения порога входа, так как весь проект — первый опыт автора в программировании.

## Уникальные подходы и методология разработки

- **Итеративный подход "снизу вверх"**: вместо попытки сразу спроектировать всю систему, проект строился слоями — сначала статичная вёрстка, затем локальное состояние React, затем собственный API, затем настоящая база данных. Каждый слой был протестирован перед переходом к следующему, что снижало риск сложных ошибок на старте.
- **Осознанный отказ от готовых библиотек аутентификации** (например, NextAuth): логин и пароль реализованы вручную (хеширование через bcrypt, сессия через httpOnly cookie), чтобы полностью понимать и контролировать каждый шаг процесса авторизации.
- **Миграция данных при смене идентификатора пользователя**: при смене имени пользователя все связанные записи (посты, комментарии, лайки, подписки, уведомления) переносятся на новое имя одной транзакцией из нескольких SQL-запросов, чтобы не терять целостность данных.
- **Отладка через прямые SQL-запросы**: на всех этапах для диагностики использовался built-in SQL-редактор Vercel/Neon — это позволяло быстро проверять фактическое состояние базы данных, а не полагаться только на логи приложения.

## Как это устроено

- `app/page.tsx` — главная страница: лента, создание поста, поиск, уведомления
- `app/login/page.tsx` — вход и регистрация
- `app/profile/page.tsx` — профиль: аватарка, смена имени и пароля
- `app/api/auth/*` — регистрация, вход, выход, текущий пользователь, смена логина/пароля/аватарки
- `app/api/posts/route.ts` — CRUD для постов, лайки
- `app/api/comments/route.ts` — комментарии
- `app/api/follows/route.ts` — подписки
- `app/api/notifications/route.ts` — уведомления
- `app/api/upload/route.ts` — загрузка фото к постам
- `app/api/generate/route.ts` — генерация текста через AI

Все обращения к базе данных и внешним сервисам происходят только на сервере (в API-роутах), никогда напрямую из браузера.

## Установка и запуск локально

```bash
git clone https://github.com/nilovichwork/bailanysta.git
cd bailanysta
npm install
```

Для подключения к базе данных, хранилищу файлов и AI нужен файл `.env.local` (не хранится в репозитории по соображениям безопасности). Получить его можно через Vercel CLI:

```bash
vercel link
vercel env pull .env.local
```

Затем запустить сервер разработки:

```bash
npm run dev
```

Открыть в браузере: http://localhost:3000

## Процесс проектирования и разработки

Разработка велась пошагово, без опыта программирования до начала проекта:
1. Создание проекта Next.js, базовая форма поста и лента
2. Собственный API-роут для хранения постов (сначала в памяти сервера)
3. Вторая страница и роутинг
4. Деплой на Vercel
5. Бонусы: тёмная тема, лайки, скелетоны, поиск
6. Обнаружена ненадёжность хранения данных в памяти на serverless-платформе — подключена настоящая база данных Postgres
7. Редактирование постов, подписки, уведомления, AI-генерация контента
8. Полноценная система логина/пароля с переносом всех связанных данных при смене имени
9. Ограничение лайков (один пользователь — один лайк), удаление постов и комментариев
10. Загрузка фото к постам через Vercel Blob
11. Полный редизайн интерфейса — фирменный градиентный акцент, аватарки пользователей
12. Настройки профиля: смена логина, пароля и аватарки

## Компромиссы

- Хранение данных в памяти сервера рассматривалось на старте как способ сэкономить время, но оказалось непригодным для serverless-окружения — пришлось перейти на полноценную БД раньше, чем планировалось изначально.
- Пароли хешируются, но нет проверки их сложности при регистрации — для тестового задания это признано допустимым упрощением.
- Уведомления обновляются только при обновлении страницы, а не в реальном времени (не использован WebSocket/polling) — ради экономии времени и сложности реализации.
- Нет ограничения размера/типа загружаемых файлов на клиенте (только на уровне самого Vercel Blob) — можно было бы добавить валидацию перед отправкой.

## Известные баги / ограничения

- Нет валидации сложности пароля при регистрации
- Нет клиентской валидации размера/типа загружаемых файлов
- Уведомления не обновляются в реальном времени — только при обновлении страницы
